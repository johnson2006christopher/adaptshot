## Preamble

AdaptShot is not merely a library. It is an argument.

The argument is this: **world-class AI does not require GPUs, cloud infrastructure, or massive carbon footprints.** A library designed from first principles for resource-constrained environments — CPU-only, memory-bounded, offline-capable, and human-aligned — can be more trustworthy, more accessible, and more impactful than systems built without constraints.

We reject the prevailing narrative that "bigger models, more data, higher carbon" is the only path forward. We assert that **constraints are not limitations — they are design principles that produce better, more generalizable, and more honest AI systems.**

This constitution is the governing document for every contributor and every AI agent that works on AdaptShot. It defines what we build, how we build it, and — equally important — what we refuse to build.

---

## I. Mission

> Democratize trustworthy, CPU-first, human-in-the-loop few-shot vision AI for resource-constrained environments.

AdaptShot enables accurate, calibrated, and offline-capable image classification with **fewer than 50 labeled examples per class**, requiring no GPU, no cloud connectivity, and no corporate infrastructure. It serves the agricultural extension officer in rural Tanzania, the conservation ranger without internet, and the clinic with a 10-year-old laptop — before it serves the well-funded research lab.

---

## II. Vision

AdaptShot will become the **reference implementation for constraint-first, human-aligned few-shot learning** — the library that researchers cite when they need trustworthy uncertainty estimates, that practitioners deploy when they can't afford GPUs, and that educators use to teach rigorous, honest AI.

By 2030, AdaptShot will have:

- **Peer-reviewed validation** of every major algorithm in top-tier venues
- **Field deployment evidence** from partnerships in the Global South
- **Plugin architecture** enabling community-contributed backbones, calibration methods, and conformal scores
- **Carbon-negative CI/CD** with verified offsetting
- **Stable, semver-governed APIs** that researchers and production systems can depend on
- **A diverse, global contributor community** that includes the people AdaptShot is designed to serve

## III. Core Engineering Constitution

These ten principles are **non-negotiable**. Every design decision, every pull request, and every architectural proposal must satisfy all of them. Violating any one is a design failure.

| # | Principle | Rule |
|---|-----------|------|
| **P1** | **CPU-First** | All operations default to `device="cpu"`. GPU acceleration (CUDA, MPS) is opt-in and must never be assumed. No code path may require a GPU. |
| **P2** | **Memory-Bound** | The full inference pipeline must operate within **<250 MB RAM**. Peak memory must be measured in benchmarks, not estimated. Support embeddings must use `float32`. Large support sets (>1000) must use memory-mapped storage. |
| **P3** | **Deterministic** | Fixed seeds produce bit-identical outputs across runs. `verify_determinism()` must pass for every operation that claims reproducibility. Non-deterministic operations require explicit opt-in and documentation. |
| **P4** | **Human-in-the-Loop** | Corrections are first-class learning signals — routed, weighted, and acted upon. Human feedback updates calibration, triggers fine-tuning, and influences buffer management. No model operates autonomously in production without a correction path. |
| **P5** | **Transparent** | Every prediction returns calibrated confidence, uncertainty decomposition (epistemic, aleatoric, distributional), OOD flags, and neighbor metadata. The library is honest about what it knows and what it doesn't. |
| **P6** | **Carbon-Aware** | Joules-per-inference and CO₂ estimates are measured in benchmarks. `eco_mode` with early-exit thresholds is the recommended default. Feature proposals must answer: "Is the marginal accuracy gain worth the carbon cost?" |
| **P7** | **Offline-Capable** | Zero internet requirement. No cloud APIs, no telemetry, no phoning home, no SaaS dependencies. Every demo, example, and test must run without network access. |
| **P8** | **Torch-Optional** | Core library imports and runs inference without PyTorch (via ONNX Runtime backend). Training features require `adaptshot[torch]`. No hard `import torch` at module level — lazy imports only. |
| **P9** | **Correctness Over Convenience** | Never sacrifice accuracy for speed. Never ship code that "probably works." Every algorithm must be verified against its source paper. Every edge case must be tested. |
| **P10** | **Explicit Over Implicit** | No silent fallbacks. No swallowed exceptions. No magic default values that change behavior without explicit user opt-in. Configuration is explicit and frozen. |

## IV. Design Philosophy

### How We Make Decisions

1. **Simplicity scales. Complexity impresses temporarily and fails permanently.** Prefer solutions that a new contributor can understand in 10 minutes.

2. **Design for the 80% use case.** The agricultural extension officer with 5 photos per disease class is more important than the researcher with 50,000 labeled images.

3. **Constraints breed creativity.** When resources are limited, engineers are forced to find elegant solutions. Embrace the <250MB budget as a design tool.

4. **Optimize for the next 10 years, not the next release.** A well-designed API from 2026 should still feel natural in 2036.

5. **Measure, don't assume.** Every claim about accuracy, latency, memory, or carbon must be backed by reproducible benchmarks.

6. **Document decisions, not just code.** Every architectural choice must be explainable to someone who wasn't in the room.

### Configuration Philosophy

- `AdaptShotConfig` is a **frozen dataclass** — immutable after creation, with `Literal` type constraints on all enumerated fields.
- Every config field has a **sensible default** that works for 80% of use cases.
- Cross-field validation is enforced at construction time (`__post_init__`).
- No hidden global state. No environment-variable-based behavior changes that aren't documented.

### Error Handling Philosophy

- All AdaptShot exceptions inherit from `AdaptShotError`.
- Error messages describe **what went wrong** and **what the user should do about it**.
- Failures in non-critical subsystems (buffer pruning, explanation generation) must not crash the prediction pipeline.
- Never use bare `except:`. Catch specific exception types. Log the failure. Continue or degrade gracefully.

### Logging Philosophy

- Library code uses the `logging` module — never `print()`.
- Demos, benchmarks, and scripts may use `print()` for human-readable output.
- Log levels: `DEBUG` for internal state, `INFO` for significant events, `WARNING` for recoverable issues, `ERROR` for failures that don't crash the pipeline.

## V. Architecture Doctrine

### Structural Principles

1. **Separation of Concerns** — Each ML subsystem (calibration, conformal, contrastive, uncertainty, explainability) is an independent class with a well-defined interface. `FewShotLearner` orchestrates; subsystems implement.

2. **Plugin-Ready Design** — Every subsystem interface must eventually support user-provided implementations. Today's concrete class is tomorrow's protocol. Design interfaces with this in mind.

3. **Single Source of Truth** — Configuration flows from `AdaptShotConfig` → `FewShotLearner` → subsystems. No subsystem reads environment variables or global state independently.

4. **Composability** — Subsystems should be independently testable. `FewShotLearner` should be testable with mocked subsystems. No hidden coupling.

5. **Lazy Everything** — Heavy dependencies (torch, torchvision, onnxruntime, gradio, faiss) are imported lazily through `_get_*()` accessor functions. Module-level imports of optional dependencies are forbidden.

## VI. Performance Standards

### Measurable Targets

| Metric | Target | Measurement Method |
|---|---|---|
| **Peak RAM (inference)** | <250 MB | `tracemalloc` + `psutil` in `energy_profile.py` |
| **Support embedding memory** | <50 MB for 1000 images | `support_embeddings.nbytes` |
| **Inference latency (single image)** | <500 ms on Intel i5-class CPU | `time.perf_counter()` in benchmark |
| **Inference latency (batch of 10)** | <2000 ms on Intel i5-class CPU | Batched benchmark (v0.3.0+) |
| **Startup time (first import)** | <2 seconds | `time python -c "import adaptshot"` |
| **Startup time (first backbone load)** | <15 seconds | Measured in benchmark |
| **Determinism** | Bit-exact across 3 runs | `verify_determinism(runs=3, seed=42)` |
| **CPU utilization** | Single-core (no threading requirement) | `psutil.cpu_percent()` |

### Optimization Principles

1. **Vectorize with NumPy.** Python loops over arrays are performance bugs. Use `np.dot`, broadcasting, and `np.linalg` operations.

2. **Batch backbone forward passes.** `extract_embedding()` should accept `List[Image]` and process them in one forward pass (v0.3.0+).

3. **Cache aggressively.** Support embeddings are computed once. FAISS indices are rebuilt only when the support set changes. Backbone models are cached by `(name, device)` key.

4. **Use `float32` everywhere.** `float64` doubles memory usage for negligible precision gain in embedding space.

5. **Memory-map large support sets.** >1000 support examples → `np.memmap` instead of in-memory arrays.

6. **Profile before optimizing.** Never optimize code you haven't measured. Use `benchmarks/energy_profile.py` and `utils/profiling.py`.

7. **Algorithmic complexity matters.** O(N²) operations must be documented as such and gated behind size thresholds with approximate fallbacks (e.g., LSH for >100 buffer items).

## VII. API Stability & Compatibility Policy

### Semantic Versioning

AdaptShot follows [Semantic Versioning 2.0.0](https://semver.org/):

- **MAJOR** (x.0.0): Breaking changes to the public API. Require migration guides.
- **MINOR** (0.x.0): New features, backward-compatible. May add new config fields with defaults.
- **PATCH** (0.0.x): Bug fixes, performance improvements, documentation updates.

### Public API Surface

The **public API** is defined by `src/adaptshot/__init__.py`. Everything exported from `__init__.py` is stable. Everything else (modules with leading underscores, internal helper functions) may change without notice.

### Backward Compatibility

- Public methods, signatures, and return types must not break within a major version.
- Breaking changes require a **deprecation cycle**: emit `DeprecationWarning` for at least one minor version before removal.
- Config field renames require: deprecation warning on old name → support both names for one minor version → remove old name in next major.

### Deprecation Policy

1. Mark deprecated API with `DeprecationWarning` including the migration path.
2. Document deprecation in `CHANGELOG.md` under a `### Deprecated` section.
3. Remove in the next major version (or after 2 minor versions if no major is planned).

### Experimental Features

Features gated behind `EXPERIMENTAL` config flags or marked with `ExperimentalWarning` may change or be removed without deprecation. Experimental features must not be enabled by default.

## VIII. Research Integrity Standards

### Algorithm Implementation Requirements

Every research-driven implementation must include:

1. **Paper citation** in the module docstring with full reference (authors, title, venue, year).
2. **Mathematical assumptions** explicitly documented (e.g., "assumes exchangeability of calibration and test data").
3. **Known limitations** listed (e.g., "single mean prototype cannot represent multi-modal classes").
4. **Computational complexity** stated (e.g., "O(N²) in support set size for leave-one-out calibration").
5. **Memory complexity** stated (e.g., "O(N·D) for support embedding storage").
6. **Reproducibility notes** (seed requirements, hardware assumptions, dataset version).
7. **Known failure modes** documented (e.g., "Mahalanobis distance fails when n_per_class < embedding_dim").
8. **Approximation honesty** — if a method is an approximation (e.g., perturbation proxy for epistemic uncertainty), state what the ideal method is and why the approximation is used.

### Claims Policy

- **Never claim benchmark results that are not reproducible** with `--seed 42` on documented hardware.
- **Never claim features that are not implemented** and passing tests.
- **Never claim theoretical guarantees** (e.g., "coverage ≥ 1-α") without stating the assumptions required.
- When comparing against published baselines, note methodological differences (different backbone, different training regime).

### Research vs. Production Code

- Experimental algorithms must be gated behind explicit config flags with `ExperimentalWarning`.
- Research code must not ship in the default inference path.
- Research results cited in documentation must include a reproducibility script.

| **Dev** | `pytest`, `mypy`, `ruff`, `pre-commit` | `adaptshot[dev]` | Dev environment only |

### Dependency Addition Criteria

Before adding any dependency, even optional, answer:

1. **Does this solve a problem that cannot be solved with existing core dependencies?**
2. **Does it have a CPU-only path?** (GPU-only libraries are forbidden.)
3. **Is its install size reasonable?** (>50MB requires strong justification.)
4. **Is it MIT, BSD, or Apache-2.0 licensed?** (Copyleft licenses require legal review.)
5. **Is it actively maintained?** (Last release >2 years ago is a red flag.)
6. **Does it introduce a transitive dependency cascade?** (5+ transitive deps requires review.)

### Strictly Forbidden

- GPU-only libraries without CPU fallback
- Cloud APIs, SaaS dependencies, or authentication services
- Telemetry, analytics, or any form of external data transmission
- Non-deterministic libraries without explicit opt-in
- GPL/AGPL licensed dependencies (incompatible with MIT)

## X. Security Policy

### Principles

1. **Local-only by design.** No network calls. No cloud. No telemetry. Attack surface is limited to the filesystem and user-provided inputs.
2. **No pickle deserialization.** State files use JSON + `.npy` format. `torch.load()` must only be used with `weights_only=True`.
3. **Input validation.** Image loading validates file existence, color channels (3-channel RGB required), and array shapes. File paths are resolved and validated.
4. **SHA-256 integrity.** All checkpoint files include checksums verified on load.
5. **Principle of least privilege.** Demos and examples never require root, sudo, or elevated permissions.

### Vulnerability Response

1. Security issues reported to the maintainer receive response within 72 hours.
2. Critical vulnerabilities receive a patch release within 7 days.
3. All security fixes are backported to the last 2 minor versions.
4. Security advisories are published in GitHub Security Advisories.

### Test Coverage Requirements

| Feature Type | Minimum Tests |
|---|---|
| New public method/function | Unit test + edge case test |
| Bug fix | Regression test (fails before fix, passes after) |
| New algorithm | Unit test + integration test + determinism test |
| Config field addition | Validation test (valid + invalid values) |
| Performance-sensitive code | Benchmark test with assertion on latency/memory |

### What We Test

- **Correctness**: Expected outputs for known inputs
- **Edge cases**: Empty arrays, single elements, extremes, NaN/Inf
- **Determinism**: Bit-exact reproducibility across runs
- **Error handling**: Appropriate exceptions raised for invalid inputs
- **Integration**: Full pipeline round-trips (load → predict → correct → save → load)
- **Persistence**: Corrupted files, version migration, integrity verification
- **Numerical stability**: Catastrophic cancellation, division by zero, overflow

## XIII. Benchmarking Philosophy

### Principles

1. **Reproducibility is mandatory.** Every benchmark must produce identical results given identical seeds, hardware, and software versions.
2. **Hardware must be documented.** Benchmark reports include CPU model, RAM, OS version, Python version, and package versions.
3. **Baselines must be honest.** When comparing against published methods, note methodological differences explicitly.
4. **Energy and carbon must be measured.** Accuracy alone is insufficient. Every benchmark suite includes latency, memory, Joules, and CO₂ estimates.
5. **Smoke tests validate correctness.** The `--smoke-test` flag runs a minimal deterministic pipeline that catches integration failures.

### Benchmark Suite (v0.3.0+ Target)

| Benchmark | Dataset | Metrics | Frequency |
|---|---|---|---|
| Few-shot classification | miniImageNet, CIFAR-100 | Accuracy, ECE, set size | Per release |
| Calibration | CIFAR-100 | ECE, MCE, reliability diagrams | Per release |

## XVII. Feature Lifecycle

### Feature Acceptance Criteria

A proposed feature is accepted only if it satisfies ALL of:

1. **Aligned with mission** — serves CPU-first, resource-constrained, human-in-the-loop use cases.
2. **Research-backed** — algorithm has a peer-reviewed source or pre-print with empirical validation.
3. **Performance-budget-compatible** — does not push inference beyond <250MB or <500ms single-image latency.
4. **Optional or backward-compatible** — does not force changes on existing users.
5. **Testable** — can be validated with deterministic, reproducible tests.
6. **Documentable** — can be explained clearly in docs and tutorials.

### Feature Rejection Criteria

A feature is rejected if ANY of:

1. **Requires GPU** without a CPU fallback path.
2. **Requires internet** or cloud infrastructure.
3. **Adds >10MB** to the core memory baseline without proportional benefit.
4. **Solves a problem AdaptShot's target users don't have** (e.g., billion-scale retrieval, distributed training).
5. **Duplicates functionality** already provided by a mature external library that users can install separately.

### Experimental Feature Lifecycle

```
Proposal → Experimental (gated, warnings) → Stable (default path) → Deprecated → Removed
```

Experimental features carry `ExperimentalWarning` and are disabled by default. Promotion to stable requires: benchmark validation, documentation completeness, and at least one minor version of experimental use without critical bugs.
